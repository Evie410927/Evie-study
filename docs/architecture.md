# 单词本应用架构

## 目标

本项目交付两个可直接打开和部署的单文件应用：韩语单词本与日语单词本。两端共享相同的页面结构、交互和存储协议，仅保留质量契约明确允许的语言差异。

## 系统边界

```text
用户交互
  -> KR / JP 单文件应用
     -> 内存状态 this.words
     -> SafeStorage
        -> localStorage
        -> IndexedDB 持久化降级
     -> Supabase Auth
     -> vocab_items + 同步版本元数据

质量控制
  -> config/quality-contract.json
  -> scripts/validate_project_contract.py
  -> test_vocab_apps.py
  -> GitHub Actions / 本地质量门禁
```

## 主要职责

| 模块 | 职责 | 修改时必须检查 |
|---|---|---|
| `standalone_kr_vocab.html` | 韩语数据和完整应用运行时 | JP 镜像、存储迁移、浏览器回归 |
| `standalone_jp_vocab.html` | 日语数据和完整应用运行时 | KR 镜像、`krMeaning` 特例、浏览器回归 |
| `supabase_vocab_sync.sql` | 云端数据结构、主键和 RLS | 前端 payload、认证、分页和版本协议 |
| `test_vocab_apps.py` | 静态契约及真实浏览器回归 | 两端对称覆盖、测试隔离和可重复性 |
| `AGENTS.md`、`rules/` | AI 行为、语言学习与交付流程 | 不得与质量契约和已接受 ADR 冲突 |

## 架构原则

1. `config/quality-contract.json` 是可执行质量约束的唯一数据源。
2. 架构变化必须新增或更新 ADR，同时更新契约与自动化测试。
3. 用户数据修改必须经过持久化成功确认后才能显示成功反馈。
4. 云端版本变化、删除和本地待上传修改必须通过明确的冲突协议处理。
5. 保持单文件离线交付能力；共享模块拆分应先提供可靠构建与内联产物流程，不能直接破坏 standalone 交付。
6. 页面启动必须比较 localStorage 与 IndexedDB 的有效快照；旧但非空的 localStorage 不得阻止更新的 IndexedDB 快照恢复。
7. 相近表达的展示顺序由每个源词条自己的 `manualSimilarWordIds` 数组顺序决定；详情与复习视图直接拖动卡片后持久化该顺序，不新增拖拽按钮，也不改变反向词条的独立排列。
8. 标题读音右侧的发音/记忆提示使用独立字段 `pronunciationNote`；下方中括号内容说明继续使用 `userNote`。两字段不得互相回填、覆盖或删除。列表卡片与详情弹窗标题均在读音右侧提供同一套紧凑原位组件：点击 `＋` 以空白输入追加内容，点击已有发音备注则回填全文并原位替换编辑，末尾 `×` 直接删除；完整新增/编辑词条弹窗还必须在“发音 / 罗马音标注”之后、“中文释义”之前提供独立的“发音备注”字段，新建时为空、编辑时回填现值，保存时替换 `pronunciationNote` 而不得清空或改写 `userNote`。黄色备注不得设置固定像素宽度上限，应在读音与右侧状态/星级操作区之间按内容伸展并使用全部可用宽度，仅在真实空间不足时省略；JP 列表标题须同时保留其专属 `krMeaning` Badge，因此备注使用到该 Badge 左侧为止。任一入口保存或删除后必须立即刷新列表与详情视图。已有备注与删除控件的按下阶段只隔离事件，必须等点击事件命中控件后再改变 DOM，防止点击穿透打开卡片详情；两字段分别参与本地持久化与逐字段云同步。非空 `pronunciationNote` 必须自动带有自定义 Tag `发音`：新建或修改备注时同时更新 `tags`，旧本地数据、IndexedDB 备用快照、导入和云端合并数据在归一化时全量补齐并排队同步；删除备注不自动删除 `发音` Tag，避免误删用户分类。

## 变更影响路径

```text
字段变化
  -> 新增/编辑表单
  -> 内存模型
  -> 本地持久化
  -> 云端 payload
  -> 缓存迁移
  -> 列表/详情/复习/相近表达视图
  -> KR/JP 对称测试

布局或交互变化
  -> DOM 契约
  -> CSS 与事件绑定
  -> 空状态和移动端
  -> Selenium 回归
```
