# 变更影响分析：云同步词库与版本基线一致持久化

## 问题与完成标准

- 问题：手机 localStorage 因容量限制保留 2065 条旧词库，云同步得到的 2241 条仅写入 IndexedDB；同步流程随后把新云端基线单独写入旧 localStorage，并在新版 IndexedDB 基线落盘前提示成功，导致重开时旧词库凭较新基线阻止完整快照恢复。
- 用户可观察结果：手机同步到 2241 条后关闭并重开仍为 2241 条；已经形成“2065 条旧词库 + 新基线 / 2241 条完整备用快照”的设备升级后也能自动恢复。
- 明确不在范围内：不改变 Supabase 表结构、认证、同步方向、词条字段合并或手动同步策略。
- 完成标准：KR/JP 同步成功前等待词库与基线一致持久化；无可信保存时间时，墓碑感知的严格超集恢复不被污染基线阻断；完整质量门禁通过。

## 风险与回滚

- 数据兼容风险：严格超集恢复只在本地缺少有效保存时间时启用，并排除删除墓碑，避免复活明确删除内容。
- 并发或跨设备风险：只串行等待本机快照完成，不增加自动同步，不改变云端冲突规则。
- 安全与隐私风险：不新增用户数据字段；沿用现有本地指纹与版本元数据。
- 回滚方法：回退双端基线持久化等待、启动比较顺序、ADR/契约及对应测试；现有 localStorage 与 IndexedDB 格式不变。

## 验证计划

- 新增或更新的测试：双端模拟 localStorage 大词库写入失败、基线小值写入成功、同步立即结束与重开；断言成功前 IndexedDB 已保存最新基线，并验证历史污染基线仍恢复严格超集。
- 必须运行的质量门禁：`python scripts/run_quality_gate.py`
- 部署后验证：确认 GitHub Pages 两端包含一致持久化等待与严格超集恢复逻辑，页面返回 200。
